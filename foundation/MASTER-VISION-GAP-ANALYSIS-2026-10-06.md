# MASTER VISION GAP ANALYSIS — 2026-10-06

## Purpose

This document converts the current website-evolution command into an executable product and platform programme. It is incremental by design: healthy production-oriented work already present in the repository is retained, while missing capabilities are prioritised by **Impact × Revenue × Dependency × Risk × Effort**.

The target is not a personal/CV website. The target operating model is an **Authority + Education + Intelligence + Revenue Ecosystem** in which the personal brand, Golden Talent, the knowledge system, professional services, research infrastructure and future platform services reinforce one another without collapsing into a single undifferentiated product.

---

## 1. Current repository position

### Strong foundations already present

- Bilingual public architecture under `/fa/` and `/en/`.
- Canonical, hreflang, structured-data and indexation governance with CI regression.
- Public authority surfaces: About, Academic Profile, Research, Publications, Books, Teaching, Projects, Engagements and Collaboration.
- Knowledge-hub foundations in Persian and English.
- Golden Talent public methodology plus private student, parent, teacher and adviser workspace previews.
- D1–D6, RCAS, evidence profile, Golden Path and BAHAR foundations.
- Role-scoped privacy model, consent concepts and account/privacy centre.
- Consultation intake, appointment-state architecture, commerce contracts and payment verification rules.
- Bilingual private admin console with content/SEO, assessment, commerce, consultation, identity, privacy and monitoring architecture.
- JHELA founding interface and publisher foundations.
- PWA, mobile navigation, offline shell, performance budgets and security/privacy release gates.
- Public academic CV and verified publication/citation tooling.
- Four-audience discovery logic already introduced on the public home and service surfaces.

### Structural limitation of the current stage

The repository is unusually mature at the **information architecture, policy, interface and domain-contract** layer, but many high-value flows are still previews because production authentication, database, private storage, email, calendar, payment gateway and lawful hosting/provider choices are not yet provisioned. This is the main dependency wall. Development should therefore continue in two parallel tracks:

1. **Revenue/authority work that can function before the backend is complete.**
2. **Provider-neutral platform foundations that reduce future migration and security risk.**

- Four audience pathways are visible.
- Public authority and service hubs exist.

Every consequential datum should retain:
- source
- subject
- timestamp
- version
- provenance
- confidence/quality state where defensible
- access scope

### Country modules

- verified relationships/assignments
- private object storage

- purpose-specific consent

- incident response
- secret isolation
- HTTPS

Minor/student data is never treated as ordinary CRM data.
