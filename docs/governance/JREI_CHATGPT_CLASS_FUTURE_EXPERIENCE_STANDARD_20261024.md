# JREI — Future-Ready Conversational Intelligence Product Standard

**Adopted:** 2026-10-24 · **Repository:** `drrezazadeh65/drjavadrezazadeh.com` · **Canonical branch:** `migration/bertina-linux6`

**Product ambition:** A future-ready, ChatGPT-class conversational experience designed expressly for educational intelligence, research, assessment and lifelong learning. This is a *quality and interaction benchmark*, **not** a representation that JREI is ChatGPT, uses the same underlying model, is affiliated with OpenAI, or can already perform every described task. Preserve JR's own Persian/English identity and black/gold/ivory/charcoal design; never copy another product's branding or misrepresent provider capabilities.

## Non-negotiable operating model

1. **One conversation, many governed tools.** A learner should be able to ask, investigate, compare, read, study, assess and resume a permitted workflow without navigating separate disconnected forms. The coordinator chooses available *registered* educational tools; it must not pretend to have tools it cannot execute.
2. **Real inference, no simulation.** When the separately authorised, budgeted, server-side LLM is absent, explicitly identify the static site guide. Do not call a keyword response an intelligent model answer. Show live capabilities based on the actual authenticated server result, not promotional copy or browser-selected flags.
3. **Evidence-first knowledge.** Every consequential factual claim should carry the original source identity, observation/version date, relevant excerpt/page/section and uncertainty where possible. Distinguish provider facts, source excerpts, professional judgement and generated suggestions. No fake papers, admission probabilities, answer keys, ISSNs, DOIs or scientific validation.
4. **Autonomous discovery, governed acquisition.** Automatically find candidate educational websites and public PDF, DOC/DOCX, ODT, HTML, TXT, CSV, XLS/XLSX, PPT/PPTX and other inspectable media. Record discovered URLs and provenance in the **one mother database**. Acquire and store full permitted content only when access/rights, robots/terms and security/quotas allow. Keep restricted candidates as metadata, never bypass paywalls, authentication or copyright. Preserve hashes, deduplication, timestamps, crawl errors, retries and revocation.
5. **End-to-end readable material.** When parsing is independently available and tested, ingest document text/metadata, structure, tables and references; add consented OCR/figure handling and mathematically faithful extraction as separate measured capabilities. Declaring a format discoverable does not imply its parser or scientific accuracy is live.
6. **Governed self-learning.** Record aggregate outcome/evidence metrics, detect defects and stale knowledge, compare a baseline to a challenger, propose a bounded change and measure quality, fairness, cost, latency and evidence regressions. No unreviewed auto-training from visitor data, hallucination-driven promotion or direct model self-modification.
7. **Self-development without owner busywork.** Detect engineering or schema needs, draft reviewed patches and *idempotent additive* migrations in the existing `drjavad1_store` database; run isolated tests, maintain provenance, prepare rollback and route approved low-risk changes through the existing CI/CD policy. The owner should not routinely create columns or run phpMyAdmin. Changes to credentials, payments, privacy, rights, destructive schemas or production release remain subject to explicit owner authority. Do not create parallel production databases.
8. **Practical memory under user control.** Preserve short conversational context only where technically implemented; offer long-term memory only with a granular, revocable opt-in, minimum retention, account scoping and deletion controls. Private student/child data require proper role, consent and guardian safeguards. Never claim persistent personal memory from an in-memory browser transcript.
9. **An educational agent, not an all-powerful agent.** Explain the proposed plan, show step status, cite the source and ask for human judgement before irreversible or high-consequence steps. Use the original commerce, identity, assessment, consent, security and authorised execution boundaries.
10. **Provider-neutral and resilient.** Optional approved cloud API plus bounded owner-provisioned Windows/other workers; independent costs, rate limits, TLS, secrets, backoff and circuit breakers. Bertina public pages, shop and existing data remain functional when a model or external worker is unavailable.
11. **Unified owner command centre.** Surface verified evidence of active models, queue/backlog, sources, imported bytes, archive integrity, parser coverage, schema revision, migration state, benchmark comparisons, PR proposals, error rates, budget and security events. Unknown measurements display **UNKNOWN**, never fabricated zero or success.
12. **Bilingual premium experience.** Full Persian RTL and English LTR; mobile-first (including small phones), tablet and desktop, keyboard/screen reader semantics, WCAG 2.2 AA target, reduced-motion support, safe-area aware layout, visible stop/cancel and transparent status. Preserve existing URLs, canonical/hreflang, search accessibility, PWA, store and current brand architecture.

## Progressive user experience

**Entry:** concise welcome, visible difference between local guide and live AI, suggested learner prompts, understandable consent. No forced registration to read public guidance.

**Conversation:** multi-turn context when live, question clarification, structured source-grounded answers, user-directed copy/new conversation, citations and links, expandable action details, accessible error/retry and graceful static fallback. Voice, file upload, multimodal analysis and persistent memory are *future capabilities* until independently implemented and accepted.

**Knowledge workflow:** discover -> rights check -> fetch -> archive -> extract -> classify -> deduplicate -> verify -> cite -> retrieve -> answer -> log scientific feedback. Invalid or unreviewed material is not promoted into authoritative educational advice.

**Engineering workflow:** monitor -> identify -> reproduce -> risk-evaluate -> draft patch/additive migration -> isolated test -> PR -> approved deploy -> post-release evidence -> rollback readiness. A plan is not a completed action; UI status is grounded in run/job/commit identifiers.

## Mandatory acceptance demonstrations before declaring "ChatGPT-class LIVE"

- Two real bilingual multi-turn model sessions, with actual provider logs and user consent; no replay/mock substituted.
- At least one verified real PDF, DOCX and HTML case, including content extraction, source provenance, hashes and legally permitted archive storage.
- Retrieval with inspectable citations and clear rejection of unsupported high-stakes inferences.
- An end-to-end approved learner tool handoff without cross-account data access.
- A consensual memory lifecycle test if memory is advertised; otherwise explicit "unavailable".
- Evidence/benchmark-driven improvement proposal showing tests, version, risk and reason, with no silent model retraining.
- An idempotent additive migration on a test clone of the original mother database, followed by rollback/recovery verification and separate authorised production rollout.
- Continuous authorised source discovery respecting robots, rights, quotas, storage and duplicate suppression; report real queue and downloaded bytes rather than promises.
- PHP/MySQL/API budgets, source isolation, rate limits, consent, accessibility on mobile/RTL, keyboard, SEO and existing store regression tests.
- Current live release SHA, CI results and post-deployment smoke evidence must match; only owner-approved protected workflow may deploy.

## Current implementation truth (snapshot, not a live certificate)

- The public browser guide is already implemented. The server-side model runtime exists as staged, independently gated code; **real live inference is not verified**.
- Universal link discovery primitives, source-policy gates, private archive architecture and evidence-gated improvement proposal code have been committed. This does **not** establish live Word/PDF parsing, a continuously running crawler, completed self-training or autonomous production schema changes.
- The assistant's bilingual copy-answer/new-chat actions and mobile full-screen styles are staged in source; their final acceptance depends on CI, visual checks and release.
- The mother DB, protected Bertina host, current deployment workflow and prior working features are canonical. No parallel store, wholesale rebuild or backward feature removal.

**Forward-only release rule:** ship only measured, incremental improvements. Treat `SOURCE`, `CI_PASS`, `PRODUCTION_DEPLOYED` and `PROVEN_LIVE` as four different statuses. The owner controls production publication, and neither an AI-generated plan nor a green source-only test establishes live model, training or download activity.
