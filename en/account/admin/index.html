2. Events and notifications

Verified registrations, orders, confirmed payments, service requests, administrator alerts, prioritisation and deduplication

Planned integration with the existing outbox and mother database
Development brief for this area

An implementation brief for future work; verify the latest code and release state before acting.

Objective: Reliable alerts for registration, validated payment, services, articles and critical errors

Prerequisites: Account lifecycle, order state machine, existing commerce_outbox, privacy and email transport

3. Health, logs and diagnosis

Error monitoring, event tracing, alert grouping, health checks, incident response and critical-error escalation

Design only; no fabricated telemetry.
Development brief for this area

An implementation brief for future work; verify the latest code and release state before acting.

Objective: Detect, group, prioritise and alert on faults without slowing public pages

Prerequisites: Correlation IDs, redaction policy, external monitoring and resource budgets

Development instruction: Create one log, trace and metric contract across PHP, MySQL, service, JavaScript, Cron and workers. Fingerprint repeated errors; expose bounded live views only during MFA sessions. Connect critical failures to alerts and incidents, redact secrets, and preserve minimal monitoring when the main database is degraded.

Acceptance criteria: Isolated fault injection triggers audited diagnosis and notification without data leakage or performance regression

4. Thirteen-engine controls

Independent pause controls, dependency mapping, read-only mode, safe mode, access governance and change audit

Operational switches require tests and authorisation.
Development brief for this area

An implementation brief for future work; verify the latest code and release state before acting.

Objective: Independent shutdown and safe mode for each engine without disabling security or auditing

Prerequisites: 13-engine registry, dependency graph and action authorization contracts

Development instruction: Implement RUNNING, READ_ONLY, PAUSED, SAFE_MODE and DISABLED with separate feature, collection and execution controls. Persist actor, reason, dependency impact, expiry and rollback. Preserve login, audit, in-flight finance and sensitive workflows; require fresh MFA and approvals for risky changes.

Acceptance criteria: Isolated disable/restore tests, audited dependency handling and uninterrupted essential services

5. Scheduling and cache

Job queue, scheduler, resource limits, layered caching, scoped invalidation and safe refresh

Customer sessions and financial records must remain intact.
Development brief for this area

An implementation brief for future work; verify the latest code and release state before acting.

Objective: Scheduled collection, private cache and explicit owner-triggered refresh

Prerequisites: Working Cron/Worker, existing policy tables, TTL and concurrency locks

Development instruction: Keep heavy collection off public requests. Use queued jobs, timeouts, retry/backoff and leases. Version and scope page, service, report, image, future CDN and Service Worker cache invalidation. A full purge must be staged and audited, never deleting sessions, orders or source data. Verify real scheduler installation.

Acceptance criteria: Load test, MFA refresh, provider outage, no duplicate job and no material public-page latency regression

6. Recovery and future scale

Backups and restore drills, acceptance evidence, capacity monitoring and hosting-independent migration architecture

Target capability, not a claim of verified recovery.
Development brief for this area

An implementation brief for future work; verify the latest code and release state before acting.

Objective: Proven recoverability and hosting-independent scaling

Prerequisites: Valid backup, isolated restore environment, agreed RPO/RTO, storage/queue/cache interfaces and reproducible releases

Development instruction: Restore an actual backup into an isolated environment and verify database, files and settings. Test controlled rollback only with owner approval, never automatically on production. Introduce host-independent adapters for queue, cache, storage, scheduler and notifications and certify performance on alternate infrastructure.

Acceptance criteria: Documented isolated restoration, integrity and timing, migration rehearsal and no hard requirement on Bertina-specific infrastructure
